Napster Companion API — Integration Findings, Version 2

Prepared by: AvatarAgency.ai · For: Napster Developer & Product Team Date: 2026-07-20 · Supersedes: Integration Bug Report v1 (26 items, 2026-06-21)

Why this report exists

Between June and July 2026 we took the Napster Companion API from first contact to a production fleet: eight live avatars across seven public web properties, including photoreal digital twins of real people, illustrated character avatars, stock-companion concierges, a lead-capture tool integration, and a mobile-framed interactive experience.

We are not reporting these issues as complaints. We are reporting them because we are almost certainly the integrator who has hit the most edges of this platform, and every item below cost us time that the next partner shouldn't have to spend. Where the platform impressed us, we've said so. Where we were wrong in our first report, we've corrected ourselves.

Version 1 (June 21) contained 26 findings. This version contains 84 (83 as compiled 2026-07-20, plus finding 84 added 2026-07-23), reflecting six additional weeks of production operation — including embedding, sessions and webhooks, tool calls, fleet-scale rebuilds, and a full account outage.

Correction to Version 1 — please disregard v1 item #1

[CORRECTED] Our first report stated that a personal Microsoft account (@gmail.com) would deploy but never activate, and that an Entra/business identity was required. This was wrong. Our own build log shows the personal account worked correctly once the Microsoft.SaaS resource provider was registered (Finding 1 below). The symptoms we attributed to account type were caused by the missing provider registration plus the activation-propagation delay. We're flagging this prominently so it doesn't propagate into your docs or support scripts.

MODULE 1 — Account, Subscription & Billing

1. [RESOLVED] Microsoft.SaaS provider must be registered manually — CRITICAL Deployment fails with raw MissingSubscriptionRegistration ("subscription not registered to use namespace 'Microsoft.SaaS'"). Fix: Subscriptions → Settings → Resource providers → Microsoft.SaaS → Register → redeploy. *Suggested:* pre-flight check in the create blade, or register on the offer's behalf.

2. [OPEN] Azure Create blade hangs the browser — MEDIUM "Page Unresponsive" during Review + Create; Chrome never completed. Microsoft Edge succeeded where Chrome failed. Clicking "Exit page" loses the form. *Suggested:* lighten the blade; document the Edge workaround.

3. [OPEN] Subscription activation propagates slowly behind a misleading error — HIGH After a successful deploy, the dashboard reports "Talking with Companions is currently disabled. No active subscription," and API-key creation returns "Access is denied." Observed propagation: 15–60+ minutes. "Access is denied" reads as a permissions problem and sends integrators down the wrong path (billing upgrades, account types). *Suggested:* a "provisioning — this can take up to an hour" state, and an error that names propagation rather than permissions.

4. [NEW][OPEN] Marketplace SaaS auto-renew defaults to OFF → full fleet outage — CRITICAL Our 1-month SaaS subscription reached term end and self-cancelled. The org went inactive and all eight token endpoints returned 401 simultaneously, on the morning of a partner meeting. Dashboard: "Your subscription is inactive. Your AI agents are paused." *Suggested:* default auto-renew ON, or surface it as an explicit choice at purchase with a consequence statement ("your agents will stop on this date").

5. [NEW][OPEN] A cancelled SaaS subscription is terminal — no reactivate-in-place — HIGH An "Unsubscribed" record cannot be revived; the only path is a fresh purchase creating a new SaaS object. A lapsed payment becomes a re-plumbing exercise. *Suggested:* reactivate-in-place for a lapsed subscription within a grace window.

6. [NEW][OPEN] Azure-subscription-Active ≠ SaaS-subscription-Active — HIGH During triage the Azure subscription showed ACTIVE and billing normally while the separate Marketplace SaaS record showed Unsubscribed. The visible object was healthy; the buried one was dead. This cost hours of misdirected diagnosis. *Suggested:* surface SaaS-subscription state in the Napster dashboard explicitly.

7. [NEW][OPEN] Repurchase did not remap to the existing org (~24h outage) — CRITICAL Azure reported "Subscribed / configured successfully," but the new subscription was never attached to our existing org. 401s persisted 2+ hours, then ~24 hours total until manual intervention. A follow-up call is still required to bind it permanently. *Suggested:* an automated "attach this subscription to my existing org" path.

8. [NEW][OPEN] "Create native integration" silently spawns a second org — HIGH The Create button on the SaaS Overview provisions a new org with a new API key rather than attaching to the existing one — with no warning that this orphans your existing fleet's identity. We avoided it only because we guessed. *Suggested:* a confirmation dialog naming the consequence.

9. [NEW][OPEN] Expiration notices carry no named consequence — MEDIUM Notices were sent, but generic in styling and silent on what would actually happen. A warning that doesn't name the consequence isn't a warning. *Suggested:* Napster-side T-7 / T-1 notices: "your agents stop on [date]."

10. [NEW][OPEN] Wrong-tenant sign-in throws bare AADSTS90072 — MEDIUM No guidance toward the tenant mismatch.

11. [RESOLVED] Temporary credentials expire silently → 401 with no re-auth path — CRITICAL A working key began returning 401; the identity portal showed "You don't have a profile set up for this application yet," with no self-serve recovery. Root cause was a temporary hackathon credential — discoverable only by asking. *Suggested:* label non-permanent credentials as such, with an expiry date visible.

12. [NEW][OPEN] Undocumented concurrency limit on token minting — MEDIUM Rapid consecutive session-token mints return intermittent 502s. Each mint creates a real connection; the limit isn't published. *Suggested:* document the limit and return 429 rather than 502.

13. [OPEN] The published per-minute figure isn't the all-in price — HIGH $0.01/min is the bring-your-own-model runtime rate. The Napster-hosted default measured ~$0.05/min all-in against real Azure invoices — a 5× gap discovered after billing. The same ambiguity applies to NV2's launch pricing, which is video-model-only with LLM inference billed separately. *Suggested:* publish an all-in figure per deployment path.

14. [OPEN] No published partner/wholesale pricing — MEDIUM Open: partner discount vs list; resell-and-markup vs client-pays-Azure; minimums or seat fees; confirmed inference cost under the managed deployment.

MODULE 2 — Companion & Agent API

15. [OPEN] Deployment type "Custom" kills sessions ~3s in — CRITICAL Sessions connect, log *Connecting → Connection established → SDK ready*, then die with provider_connection_aborted. The single most confusing failure mode we encountered: it presents as an SDK or network fault. Root cause is that "Custom" expects a bring-your-own Azure OpenAI real-time endpoint. Fix: recreate the key with Deployment = Napster. *Suggested:* reject key creation with "Custom" if no endpoint is configured, or return an error naming the deployment type.

16. [OPEN] language: "English" returns 400 — must be ISO 639-1 "en" — MEDIUM Undocumented. *Suggested:* state the expected format, or accept common language names.

17. [OPEN] POST /public/faqs/{id}/items returns HTTP 500 consistently — HIGH Repeatable 500 with a validated-correct {question, answer} shape. We now skip the FAQ layer entirely and inline FAQ content in agent instructions as a standing fallback.

18. [OPEN] GET /public/ethnicities 404s, but ethnicity is mandatory — HIGH The documented enum-discovery endpoint doesn't exist, yet the field is required on /digital-twins. We discovered working values ("white", "multiracial") by reading the 400 response. Note the field is required even for non-human characters — we shipped a watercolor dog that needed an ethnicity. *Suggested:* restore the endpoint, publish the enum, and make it optional for non-human twins.

19. [RESOLVED, residual] DigitalTwinConsentRequired with no pointer — CRITICAL The first real /digital-twins call returns this error with no link, no dashboard reference, no doc URL. The consent gate is one-time and org-wide, granted via Dashboard → Companions → New Digital Twin. Because plain /companions doesn't trigger it, an org can operate for weeks and hit this cold. The doc exists (thank you) — but was only found when it was sent to us directly. *Suggested:* put the URL in the error body.

20. [RESOLVED, by explanation] version:"v2" silently completes as v1 — CRITICAL POST /public/digital-twins with version:'v2' and a spec-compliant reference video returned success, then completed as versions:["v1"]. The create response never echoes version, so there was no signal. We reproduced it twice across different hosts and spent days chasing a plausible-but-wrong hypothesis (video content-type) before your team confirmed v2 is private-preview-gated. Our build was correct the entire time. *Suggested:* reject or warn on version:'v2' for non-entitled orgs, and echo version in the create response. This single change would have saved us the most time of anything in this report.

21. [NEW][OPEN] Dashboard "New Digital Twin" is image-only, making v2 API-exclusive — MEDIUM Appearance accepts only an image ("Must be 16:9") with no video path — so the only way to attempt v2 is the API, which then silently produces v1.

22. [OPEN] v2 processing time documented only as "several hours" — MEDIUM No range, no status endpoint, no webhook. We cannot give clients a timeline or build a progress UI.

23. [NEW][OPEN] No GET /public/digital-twins/{id} — MEDIUM Status must be read from GET /companions/{id}. Twins are companions, but the resource asymmetry isn't documented; we found it by trial.

24. [NEW][OPEN] Digital-twin create response omits status — MEDIUM No way to confirm from the create call that processing began.

25. [NEW][OPEN] All four identity fields mandatory for twins, optional for companions — LOW firstName, lastName, gender, ethnicity. The asymmetry isn't called out.

26. [OPEN] Companion status flow undocumented; CompanionNotReady reads as an error — MEDIUM Actual flow: pending → generationCompleted → readyToUse → completed (~2–3 min). Connecting early returns CompanionNotReady, which is a healthy signal that reads as a failure.

27. [NEW][OPEN] Bare ConnectionCreationFailed with no diagnostic detail — MEDIUM No indication that the root cause was account provisioning.

28. [NEW][OPEN] Auto-generated assistantPrompt overrides custom instructions — HIGH Napster generates an assistant prompt from description, and its injected "I am the digital twin" identity rules win over the agent's own instructions for the opening message — avatars greet with "I am the digital twin… How can I help you?" regardless of authored greeting. Working fix required both: embedding greeting behavior in description *and* front-loading an override in instructions. Either alone fails. *Suggested:* document the precedence, or expose the generated prompt for editing.

29. [NEW][OPEN] No companion-swap on an existing agent — HIGH To move a configured agent (persona, FAQ, knowledge) onto a new face or voice, there is no documented PATCH. The fallback is building a new agent and re-supplying everything, which changes the agent ID and forces a redeploy of every token endpoint pointing at it. At fleet scale this is the single biggest operational tax we carry. *Suggested:* PATCH /agents/{id} with a companionId field.

30. [NEW][OPEN] CompanionInUse blocks deletion without stating the remedy — LOW The agent must be deleted from the dashboard first; there's no cascade and no hint.

31. [NEW][OPEN] Function IDs are the tool's name, not a UUID — MEDIUM POST /public/functions returns an id equal to capture_lead. Surprising, and it created a real hazard: every agent rebuild must re-attach the function or the tool silently detaches with no warning. We now enforce this by checklist. *Suggested:* warn when an agent is created without previously-attached tools.

32. [NEW][OPEN] Tool-call payload schema undocumented — HIGH No published shape for what Napster POSTs to a tool URL; the 10-second response window is the only known constraint. We shipped defensive parsing and raw request logging to discover it in production.

33. [NEW][OPEN] Webhook payload schema undocumented; docs page didn't resolve — HIGH session.started / session.closed exist with a per-webhook signing secret, but the payload JSON is unconfirmed and the documentation page failed to load.

34. [NEW][OPEN] Session transcript retention period undocumented — HIGH This blocks any client-facing promise about conversation history and forced us to make our own database the system of record.

35. [NEW][OPEN] Lead contact info isn't structured on the session record — MEDIUM Name, email and phone exist only as free text inside conversation.items[].text. Structured lead delivery requires a custom tool or transcript scraping.

36. [OPEN] Companion/agent count limits per subscription undocumented — MEDIUM Asked June 19, re-asked since; still unanswered. This directly gates how we price and plan fleet growth.

37. [NEW][OPEN] Multilingual behavior is contradictory — MEDIUM language takes one ISO code per agent and the platform describes that constraint to the model — one of our agents volunteered "I can only speak English" unprompted. Meanwhile the v2 docs advertise lip-sync during "language switching," and the underlying realtime model is inherently multilingual. Open: can one agent speak many languages if instructed; is per-language-agents-on-one-twin the intended pattern; does a cloned voice preserve likeness across languages.

38. [NEW][OPEN] Stock-companion listing pagination undocumented — LOW GET /public/companions/napster-stock defaults to 10. Retrieving the full 2,000+ library required blind-probing five limit parameter names and two offset schemes.

39. [RESOLVED] Stock-companion commercial licensing was undocumented — HIGH Whether an org may deploy stock companions on clients' sites as branded spokespeople was unpublished, and first-line support escalated rather than answered. Answered directly and clearly on Discord (2026-07-13): no restrictions, commercial use permitted. Thank you — this unblocked a product line. *Suggested:* put it in the docs.

40. [NEW][OPEN] Agent temperature may not be settable via API — MEDIUM A dashboard-only setting that can't be reproduced programmatically breaks rebuild parity.

41. [OPEN] Voice-clone guidance is thin — MEDIUM Documented: mp3/wav/m4a/flac/ogg/webm/mp4, ≤10 MB, 60–300 s, public HTTPS. Undocumented: optimal length, required audio quality, processing time, supported languages, consent requirements. Our production recommendation (3–5 minutes of natural, unscripted speech) came verbally from your team, not the docs.

42. [NEW][OPEN] Memory documented at the rule level, not the mechanism level — MEDIUM Documented: externalClientId format and matching rules, externalClientProfile. Undocumented: how memory is surfaced to the model, memory limits (session count, decay, token cap), and whether returning-visitor greeting is automatic or must be prompted.

MODULE 3 — Assets & Media

43. [OPEN] A 12 MB PNG pictureUrl returns HTTP 500 — HIGH Twin creation fails with a bare 500. A sub-1 MB JPEG succeeds. An undocumented size/format limit surfacing as a server error rather than a 4xx validation message.

44. [OPEN] pictureUrl spec is incomplete — HIGH Documented only as "16:9, waist up, well-lit, looking into camera" — no formats, no minimum resolution, no maximum file size. This directly causes Finding 43.

45. [NEW][OPEN] V1 auto-extracts an arbitrary frame from a supplied video — MEDIUM Our first client twin looked poor because a random video frame became the source image. Rebuilding V1 explicitly from a sharp studio headshot produced a dramatically better result. The create response echoing pictureUrl was the only signal that the right path was taken. *Suggested:* document that an explicit still beats a video-derived frame for V1 quality.

46. [NEW][OPEN] No ingestion diagnostics for reference media — MEDIUM With no version echo and no ingestion feedback, we spent days on a plausible-but-wrong hypothesis about video content-type headers. Any per-asset ingestion status would have ended that immediately.

47. [OPEN] All media must be public HTTPS; no upload or signed-URL path — MEDIUM Every integrator must solve hosting before they can call the API, and client media must sit at a publicly reachable URL — which is a real conversation with privacy-sensitive clients. *Suggested:* an upload endpoint or signed-URL ingestion.

48. [NEW] POSITIVE FINDING — illustrated / non-human characters work A face-forward 16:9 watercolor dog was accepted by /digital-twins v1, lip-syncs at fair quality, and carries a unique cloned voice. We've shipped it to a children's-book client. We're flagging this as a validated use case you may not know you support — it opens publishing, education, and character-IP markets. (Necessarily V1, since V2 requires video of the subject.)

49. [NEW][OPEN] NV2 capture spec vs the v2 video path is unclear — MEDIUM Does NV2 publish a capture spec distinct from the v2 path, and is NV2 the engine behind v2 twins or a separately-invoked model?

MODULE 4 — Web SDK & Embedding

*This module is where we spent the most engineering time, and where a small amount of work on your side would have the largest effect on how professional partner deployments look.*

50. [OPEN] avatarStyle: { view: 'circle' } is ignored — MEDIUM The documented option has no effect, and the CSS fallback (clip-path: circle(50%)) produces a black split-screen artifact. We abandoned circular avatars entirely.

51. [OPEN] The SDK overrides host CSS on activation — HIGH On session start it rewrites border-radius, border color, and dimensions on the host container.

52. [OPEN] The SDK expands its mount and defeats standard containment — HIGH aspect-ratio, contain: size, and padding-bottom sizers all failed. A JS height-lock was the best available workaround and still changed shape in talk mode.

53. [NEW][OPEN] The SDK injects a position: fixed wrapper that escapes its card — HIGH Working fix: transform: translateZ(0) on the frame plus [class*="-fixed"]{position:absolute!important; inset:0!important}. Related trap: setting transform: none on an ancestor releases the widget to fullscreen, so sliding panels must keep translateX(0) when open.

54. [NEW][OPEN] The SDK injects body,html{background:transparent} and never removes it — HIGH The host page turns white when a session starts and stays white after it ends. We now ship a snippet on every page that captures computed backgrounds at load and re-asserts them with !important. *Suggested:* scope the injected style to the SDK's own container.

55. [NEW][OPEN] Inner SDK panels overflow-scroll, showing scrollbars in the frame — MEDIUM

56. [NEW][OPEN] The container renders a white border/radius edge that can't be styled away — MEDIUM We crop it with a deliberately oversized mount (inset:-4px).

57. [OPEN] Built-in controls aren't suppressible and overlap the avatar's face — HIGH Unusable framing for marketing-grade embeds where the face is the product.

58. [OPEN] The AI-disclosure banner can't be positioned or styled — MEDIUM To be clear: we support the disclosure and ship our own alongside it. The friction is the absence of a styling/positioning API, not the element's existence.

59. [NEW][OPEN] The SDK's hang-up button doesn't notify the host page — CRITICAL Clicking the built-in hang-up ends the session and stops metering, but host JS receives no callback unless an onDestroy handler was passed. Our page showed a session countdown running to zero over an empty white box after the user had already hung up. onDestroy, onStateChange and onAvatarReady exist but are under-documented. *Suggested:* fire a default event on teardown, and document these callbacks prominently. This one ships broken UI by default for anyone who doesn't know to look.

60. [NEW][OPEN] Mic permission is requested inside init() with no way to defer — HIGH Verified against both the SDK bundle and its README. This makes connect-before-prompt architecturally impossible and forces a slower perceived load. *Suggested (feature request):* a deferMicPermission option.

61. [NEW][OPEN] The ready callback fires while the loading animation is still on screen — MEDIUM We gate on video.videoWidth >gt; 0 plus advancing currentTime instead of trusting it.

62. [NEW][OPEN] No usable conversation-start / state event — MEDIUM SDK state events never matched any conversation-start pattern, so metering and countdown UI can't be driven from them.

63. [NEW][OPEN] features.showSDKLoader.enabled = false is undocumented — LOW Found by reading the bundle.

64. [OPEN] SDK distribution path and global name are wrong in the docs — HIGH The standalone build is at /lib/index.standalone.js (not /dist/) and the global is napsterCompanionApiSDK. Worse, a hard-coded "requires X domain" error message masked the real path/global error, sending debugging in entirely the wrong direction. *Suggested:* fix the docs and remove the misleading hard-coded error.

65. [OPEN] Hiding the placeholder on session start collapses host layout — LOW

66. [OPEN] Dark backgrounds bleed through semi-transparent placeholder edges — LOW

67. [NEW][OPEN] Nothing prevents an auto-starting embed from silently burning minutes — HIGH One of our pages minted a token and opened a real session on every page load — invisible, continuous metering. We now enforce user-initiated sessions as a QC gate. A related trap: re-initializing inside onDestroy makes hang-up appear broken *and* leaks spend. *Suggested:* an idle or auto-start guard, or simply a warning — this protects integrators from self-inflicted cost and protects you from the resulting support conversation.

68. [RESOLVED] Metering-vs-timer semantics — MEDIUM Confirmed by your team: metering stops when the session ends, not at a preconfigured limit, so a page-side countdown is cosmetic and does not cap cost. *Suggested:* state this in the billing docs.

84. [NEW][RESOLVED 2026-07-24] The agent cannot speak first — no auto-greeting, no text injection — HIGH *(Added 2026-07-23; RESOLVED next day via Discord: the initialSpeech field on connection creation — POST /agents/{id}/connections, /connections, /ws-connections, plus channel-level defaults — delivers an opening in the agent's own voice at connect. Documented at developers.napster.com → session-configuration → opening-instructions. Answered within 24h of asking; deployed on our side same day. Thank you — this is the feedback pipeline working.)* A connected avatar sits silent and smiling until the visitor speaks. We verified this is architectural, not configurational: the SDK instance exposes showAvatar / hideAvatar / destroy / mute / setVolume / pause and no send method of any kind; the internal data channel (named "chat") carries only connection plumbing, settings, and tool-call outputs; and the SDK's own inactivity warning — *"Say something to keep it active"* — confirms the user-speaks-first turn model. Instruction-level fixes ("your very first words must be…") cannot work because the agent's turn never runs until user audio arrives. We rebuilt an agent specifically to test this; it changed nothing. Impact: for consumer-facing deployments this is a first-contact conversion killer — a first-time visitor meets an avatar that stares at them, and doesn't know they're supposed to talk to it. Feedback we received directly from your own partnerships team ("have her be the one to start talking") is currently impossible to implement. *Suggested:* an initialGreeting option on sdk.init() that has the agent deliver its opening line on connect, and/or a sendMessage(text) method on the instance. Either one unlocks it.

MODULE 5 — Dashboard

69. [NEW][OPEN] Toggles reset on every agent rebuild — CRITICAL Memory, Screen Share and Picture-in-Picture are per-agent, and a rebuild produces a new agent with all of them off. Silently. There's no carry-forward, no warning, and no API equivalent we could find — so a scripted rebuild always requires a manual dashboard ritual afterward. We've documented this internally three separate times because it kept biting us. *Suggested:* expose these in the agent API, or carry them forward on rebuild.

70. [RESOLVED] Dashboard shows "No data" when key and view are in different projects — MEDIUM API keys are project-scoped and companions live in the key's project. Not obvious from the key-creation UI.

71. [OPEN] Dashboard card status lags the API — LOW Cards read "Provisioning" after the API reports completed. Guidance we now follow: trust the API, not the card.

72. [NEW][OPEN] Card motion is misleading as a quality signal — MEDIUM Generated companions have an idle-motion loop on their card; digital twins display as a still image and only animate in a live session. We misread this as "the twin isn't working" and reversed a correct conclusion because of it. *Suggested:* a "preview in Playground" affordance, or a note on twin cards.

73. [NEW][OPEN] No agent versioning — same-named agents accumulate — MEDIUM Deprecated agents persist in the Playground under identical names; we tested the wrong brain more than once. One of our agents accumulated four identically-named versions. *Suggested:* versioning, or at minimum a created-at stamp in the picker.

74. [NEW][OPEN] No export path for dashboard-authored agent instructions — HIGH During a disaster-recovery audit we found two production personas existed only in the dashboard, with no way to export them — we transcribed them by hand into version control. For any team practicing infrastructure-as-code, dashboard-only state is a liability. *Suggested:* a read API for agent instructions.

75. [NEW][OPEN] Playground → Logs covers test sessions only — LOW Live site transcripts come from the Sessions API instead; the split isn't signposted.

MODULE 6 — Documentation & Support

Appendix B — What we built on the platform

Eight production avatars across seven public properties: photoreal digital twins of four real people (with written consent and on-page disclosure), an illustrated character avatar for a children's book series, stock-companion concierges, a lead-capture tool integration firing on session.closed, and a mobile-framed interactive experience. We're documenting the rough edges precisely because we intend to keep building here. A platform this capable deserves an integration path that doesn't require an integrator to rediscover it.
